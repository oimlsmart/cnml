# IA keystore backup runbook

This runbook documents how an Issuing Authority (IA) backs up and
recovers its CA keystore. It is the IA-scale analogue of the
[BIML Root backup runbook](biml-root-backup.md).

The IA keystore (`~/.oiml-pki/keystore.json` or the configured
`OIML_PKI_KEYSTORE_DIR`) holds the IA's CA private key, encrypted
under a passphrase. Loss of the keystore or the passphrase means
every cert ever signed by this IA becomes unverifiable.

## Status

Pilot. Not yet exercised against a real IA quorum. See TODO.cnml/69.

## Threat model

Same shape as BIML Root, scaled to the IA:

- **Loss.** Drive failure, facility fire, operator forgets
  passphrase. Recovery via M-of-N officer shares.
- **Theft.** A single share is stolen. Insufficient.
- **Insider.** A rogue IA officer. Their share alone is
  insufficient; M-of-N required.

## What is shared

The IA keystore's **encryption passphrase**, not the private key
itself. The keystore file (`keystore.json` + `salt.bin`) is the
encrypted blob; the passphrase is the decryption key.

The passphrase is generated by the IA's initialization ceremony
as a high-entropy random string (256 bits). It is never written
down except as Shamir shares.

## Assumptions

- The IA's CA server is air-gapped at the IA's facility.
- N=3 IA officers hold shares (the same officers who participate
  in 2-of-3 threshold signing).
- M=2 threshold for keystore recovery.
- Shares are distributed in tamper-evident envelopes.
- The keystore file is backed up to an offsite location (e.g., a
  second facility's safe, or a safety-deposit box).

## Initialization ceremony

Performed once, when the IA's CA is first set up.

### Participants

- The 3 IA officers
- The IA's security lead (chair)
- A scribe
- An independent witness (e.g., a BIML observer)

### Procedure

1. **Convene at the IA's facility.** Air-gapped.

2. **Generate the keystore passphrase.** The ceremony laptop
   generates a 256-bit random string.

3. **Initialize the CA keystore.** The passphrase encrypts the
   keystore. The IA's CA private key is generated in the keystore.

4. **Shamir-split the passphrase into 3 shares, threshold 2.**
   Run the script:

   ```bash
   ruby scripts/provision-keystore-backup.rb --threshold 2 --parties 3 \
     --passphrase <passphrase-from-step-2> \
     --output-shares <output-dir>
   ```

   The script writes:
   - `<output-dir>/share-1.txt` ... `<output-dir>/share-3.txt`
   - `<output-dir>/manifest.json`

5. **Print each share on paper.** Each printout goes into a
   tamper-evident envelope, sealed in the ceremony.

6. **Distribute the envelopes.** Each IA officer takes one
   envelope, stored in their office safe.

7. **Make the offsite keystore backup.** The `keystore.json` and
   `salt.bin` files are copied to encrypted media and stored at
   the offsite location. The passphrase does NOT travel with the
   backup — the passphrase is the Shamir-shared secret.

8. **Securely erase the passphrase from the ceremony laptop.**
   Multiple overwrites.

9. **Log the ceremony.** A `CeremonyTranscript` of type
   `ia_signing` (or `director_onboarding` for the IA scale) is
   created.

## Recovery procedure

Performed if the keystore passphrase is lost, or if the local
keystore file is lost and the offsite backup must be restored.

### Participants

- At least 2 of the 3 IA officers
- The IA's security lead (chair)
- A scribe

### Procedure

1. **Convene at the IA's facility.** Air-gapped.

2. **If passphrase lost, keystore intact:** the keystore file is
   still on disk. Skip to step 4.

3. **If keystore lost, passphrase forgotten:** retrieve the
   offsite keystore backup. Restore `keystore.json` and `salt.bin`
   to the CA machine.

4. **Each contributing officer opens their envelope.** The
   tamper-evident seal is verified by the witness.

5. **Reconstruct the passphrase.** Run the script:

   ```bash
   ruby scripts/provision-keystore-backup.rb --reconstruct \
     --input-shares <share-1.txt> <share-2.txt> \
     --output-passphrase <recovered-passphrase-file>
   ```

6. **Unlock the keystore.** Use the recovered passphrase to
   unlock the keystore on the CA server.

7. **Re-seal the shares.** Each officer's envelope is re-sealed.

8. **Log the recovery.** A `CeremonyTranscript` of type
   `key_recovery` is created.

## Operational cadence

- **Initialization:** once, when the IA's CA is first set up.
- **Offsite backup refresh:** annually, or after major key
  rotations. The offsite copy is replaced; the old copy is
  destroyed.
- **Recovery:** rare.
- **Tabletop:** annually.
